# Chiselo Product Strategy

## One Promise

Open finished HTML, refine what you see, review exactly what changed, and ship
the original format.

Chiselo is a local macOS finishing tool for existing HTML. It is not a website
builder, AI content generator, hosting platform, or general-purpose IDE.

## Primary Workflow

1. Open an existing HTML document and its local assets.
2. Check whether the document is a good candidate for direct visual editing.
3. Select visible objects and make local text, image, style, or layout edits.
4. Review changes at the required viewport and resolve delivery warnings.
5. Save the HTML or export PDF. PPTX remains a best-effort delivery option.

## Compatibility Boundary

The primary target is static HTML and conventional HTML generated by people or
other tools. Dynamic applications, cross-origin embeds, animation timelines,
server integrations, and complex framework runtimes are compatibility cases,
not promises. They must remain visibly diagnosed and require explicit trusted
mode before their scripts can run.

## Product Priorities

Before adding a feature, prefer work that strengthens one of these outcomes:

1. Preserve the user's source and local assets.
2. Make one visual change predictable and reviewable.
3. Make delivery risks visible before a file leaves the app.
4. Keep the product understandable to nontechnical users.

Do not add site management, hosting, prompt-to-page generation, or a general
code editor unless the product direction changes deliberately.

## Open Source And Brand

The source code is Apache-2.0. People may use, modify, and distribute the code,
including commercially. The Chiselo name, icon, tagline, and Vellumloop
branding remain protected so forks and paid products need their own identity.
See [TRADEMARKS.md](../../TRADEMARKS.md).

## Maintenance Rules

- Keep one product promise and one primary workflow in the README.
- Add a regression before fixing a data-loss, security, or layout-isolation bug.
- Keep `main` green; do not publish a release from a failing CI revision.
- Extract one cohesive responsibility at a time from large files. Avoid broad
  rewrites that combine behavior changes with file moves.
- Treat the bundled HTML examples as public compatibility contracts.
